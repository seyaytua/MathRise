## 🎯 このドキュメントの目的

ユーザーからの要望を管理し、対応可否を判定し、実装状況を記録する。

**参照**:
- [CORE_CONCEPTS.md](CORE_CONCEPTS.md) - 基本コンセプト
- [PROMPT_RULES.md](PROMPT_RULES.md) - 調整ルール

## 📌 記入方法

### 優先度
- **上に行くほど優先度が高い**
- 最優先 → 高優先 → 中優先 → 低優先

### 各要望の記載項目
- **要望内容**: 具体的な要望
- **要望者**: 匿名可
- **日付**: 要望を受けた日
- **カテゴリ**: 構成/内容/レイアウト
- **対応可否**: ✅/⚠️/❌
- **対応方法**: 具体的な調整内容
- **実装状況**: ⏳/🔄/✅/❌

## 📋 要望評価システム

### 評価基準

#### ✅ 対応可能（Implementable）

以下の条件を**全て**満たす場合：

1. **基本コンセプトを崩さない**
   - [ ] 「行間を埋める学習」に反しない
   - [ ] 「メリハリのある学習設計」に反しない
   - [ ] 「AI進化への対応」に反しない

2. **決まった展開を維持できる**
   - [ ] 重要度3段階（低/中/高）を維持
   - [ ] 山場の存在を維持
   - [ ] step-by-step形式を維持

3. **プロンプトで調整可能**
   - [ ] パラメータ調整で実現可能
   - [ ] モジュール追加で実現可能
   - [ ] テンプレート変更で実現可能

---

#### ⚠️ 部分的に対応可能（Partially Implementable）

以下の条件を満たす場合：

1. **基本コンセプトは崩さない**
2. **アプリ側の協力が必要**
3. **プロンプトだけでは不完全**

---

#### ❌ 対応不可（Cannot Implement）

以下のいずれかに該当する場合：

1. **基本コンセプトに反する**
2. **決まった展開を崩す**
3. **技術的に実現不可能**

---

### 評価プロセス

#### ステップ1: 要望の分類

要望内容を確認 ↓ カテゴリ分類 ├─ 構成（レッスンの順序・数） ├─ 内容（説明文・問題） └─ レイアウト（見た目）→ アプリ側


#### ステップ2: 基本コンセプトチェック

□ 「行間を埋める学習」に反しないか？ □ 「メリハリのある学習設計」に反しないか？ □ 「AI進化への対応」に反しないか？

→ 1つでも反する場合は「対応不可」


#### ステップ3: 実現可能性チェック

□ プロンプトのパラメータ調整で可能か？ □ モジュール追加で可能か？ □ テンプレート変更で可能か？

→ 全て「いいえ」の場合は「対応不可」 → 部分的に「はい」の場合は「部分的に対応可能」 → 全て「はい」の場合は「対応可能」


#### ステップ4: 優先度の設定

ユーザーが設定した優先度 ↓ 実現可能性を考慮 ↓ 最終的な優先度を決定
